## Objective and context

The user requested one visible settings section at a time instead of anchor scrolling. They then refined name semantics to Amtlicher Name (Legal name) and Bevorzugter Vorname (Preferred first name), with the preferred first name shown in chat and defaulting to the first name. Their latest decision keeps username under Login & security, saved uniquely now for future login/profile URLs; those flows are explicitly deferred. The earlier visible-username idea is superseded. Follow the [identity/privacy contract](../../../docs/mvp-spec.md#8-identity-data-and-demo-integrity) and [Account contract](../../../docs/mvp-spec.md#9-scheduling-behavior-and-permissions). Preferred first name belongs in Personal details; the separate future-use username belongs in Login & security.

## Scope and non-goals

- Personal details: optional private Legal name and Preferred first name override, birthdate and gender. Preferred first name defaults to the first word of the legal name, or retained presentation name until legal name is supplied. It is the chat identity, not a unique handle.
- Login & security: optional globally unique username reserved for future sign-in/profile URLs; canonical lowercase, 3–30 ASCII letters/digits/underscores starting with a letter. Username can be changed/cleared while these uses are deferred. Explain that sign-in/URLs are not live.
- Keep legal name/override/username in owner-only account storage and project only the effective preferred first name into authorized chats. Do not copy existing shared names into the Legal name field, rewrite original identities/snapshots or alter public coach names, booking labels, avatars or authority.
- Render exactly the selected Personal details, Login & security or Language panel, using validated query links and active navigation. Default Personal details, support deep links/Back/Forward and preserve authorized in-memory drafts across section changes.
- No username authentication, public URL routing, uniqueness requirement for first names, legal-name verification, German translation, photo controls or hosted rollout. Follow-up contract planning owns future login/URLs.

## Expected behavior and edge cases

Only preferred first name is shown as the chat counterpart name for both coach and athlete roles. Blank preference means the first word of legal name; without a saved legal name, use the first word of the existing presentation name. Existing names are not relabelled as legal identity. Private legal name never enters chat JSON, public discovery, bookings or shared actor snapshots. Account save may persist a computed chat name on profiles, without changing existing presentation names or opaque IDs. Existing chats immediately read current preferred presentation; original message contents/cards remain intact.

Username uniqueness is enforced in the database and simultaneous claims have one winner. Name conflicts return a specific username-taken state without saving other fields or exposing another account. Personal and username writes are separate commands so changing login settings cannot overwrite a hidden personal draft. Global optimistic revisions and exact retries remain; a successful own-section save may advance an otherwise current draft's base revision without overwriting its input. Stale/external changes retain a conflict draft.

Use `/account?section=personal-details`, `login-security` or `language`; invalid/repeated sections fall back to Personal details. Only the selected panel exists in the DOM. Ordinary active links and heading focus replace hash jumps. Hidden personal/login drafts remain in parent state; actor changes clear them. English/German Coming soon and current email-code sign-in retain their earlier scope.

## Implementation record

### Changes and rationale

Replaced the stacked settings sections with one query-selected panel. Personal details, Login & security and Language have ordinary active links, safe defaults and focusable section headings. Only the selected panel renders; its siblings are absent from the DOM. In-memory drafts live above the selected content so switching sections and browser Back/Forward retain them; actor/session/dataset keys still clear private state. The installed Next layout-router state key explicitly excludes search parameters, consistent with the observed retained drafts.

Personal details now edits private Legal name and Preferred first name rather than renaming the retained shared presentation name. Blank preference defaults to the first word of legal name, or the retained presentation name if no legal name was supplied. Defaults update as the legal-name draft changes. Account writes compute only a shareable first name on profiles; original display name, public coach name, booking labels, snapshots, identity, media and authority are untouched. Current chat lists/threads and authorized coach contact previews use the preferred/default first name for either role; existing message permission and media fields remain intact. Full legal name and raw name/username fields never enter chat JSON.

Username is a separate optional editor under Login & security with explicit future-use copy. It is uniquely stored and normalized, but no username authentication/profile URL is claimed. Section-specific commands prevent hidden-field writes. Username conflicts return a specific message, and database uniqueness plus profile-row locking serialize concurrent claims/saves. Exact retries retain their revision; stale altered writes conflict. Failed edits retain input. A successful own-section save can advance an otherwise current other-section draft's revision without altering its values; stale drafts remain stale. Cancel/success return focus to the correct Edit control.

### Contracts, configuration, and operations

`AccountDetails` now includes nullable legalName/preferredFirstName/username alongside retained displayName/birthdate/gender/revision. POST is a strict Personal details or Login & security command, not the former generic display-name update. New owner-only DB function `update_current_account_settings(text,jsonb,integer)` retains row locks/revisions and exact retry; username-taken maps to HTTP 409. A hard refresh/new matching frontend is required for the extended read/command shape; invalid old/foreign fields fail closed.

The additive ninth local migration is `20261017000600_account_names_and_usernames.sql`, SHA-256 `7997449018054c5f761842202be9f3cb2cf0aa4480483873ef8f13c88fca0b2b`. Existing read/message helpers retained OIDs, ownership, ACLs, security mode, volatility and search paths. No existing identity/name data was backfilled, reset or seeded. No new dependency/environment/Auth/locale configuration or hosted operation. Rollback needs a compatible Account read/command shape or reviewed forward correction; never drop private fields or rewrite installed history.
