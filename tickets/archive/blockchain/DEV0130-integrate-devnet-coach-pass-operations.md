## Objective and context

Connect the complete local coach-pass program to recoverable Devnet purchases and booking-credit operations with server-authoritative preparation, simulation, wallet approval, bounded platform payment of every transaction fee and rent deposit, and finalized pair-ledger/reservation verification.

## Scope and non-goals

- In scope: deployable program/upgrade identity; Devnet configuration; single-coach-signature authority initialization; prepare/simulate/sign/submit/verify/recover operations; token-account readiness; pair-ledger and reservation indexing; first/subsequent purchase recovery; reserve/consume/return recovery; public Explorer evidence.
- Out of scope: UI composition, booking rules, mainnet, arbitrary tokens, production custody, Kora migration or real-money claims.

## Expected behavior and edge cases

Every purchase approval identifies Devnet, test EURC, coach, exact price, purchased credits, destination and the MovX platform payer. Every booking-credit approval identifies the pair ledger, booking reference, scheduled time/cutoff, exact transition, authority and platform payer. Clients and coaches need no test SOL; the client still supplies the exact purchase price in test EURC and every business action still requires its client or coach signature. A lost response is recovered from the pair PDA, purchase nonce or deterministic reservation receipt. Wallet rejection, insufficient balance, missing token account, stale blockhash or RPC ambiguity never causes a blind repeat.

CoachAuthority initialization records the configured recovery public address but requires only the coach's user-facing wallet as business signer; the server-only platform payer still signs solely to fund the fee and rent. The recovery authority signs only a later wallet-rotation operation together with the replacement wallet. A coach is never asked to hold, fund or switch to the recovery authority during setup.

## Assumptions, decisions, and dependencies

The DEV0127 purchase contract, DEV0131 reservation contract and DEV0132 platform-payer instruction/client change are complete and stable for deployment. Credentialed RPC, platform-payer and upgrade material remain separate server/operator secrets; bootstrap configuration needs only the recovery public address. The sponsor signs only an allowlisted transaction reconstructed and validated by the server; it cannot replace the required client or coach authority. Automation may not sign or send a user-authorized transaction without that user's explicit approval.

## Implementation plan

1. Freeze deployment/configuration, bounded platform-payer policy and operation records against DEV0132's completed interface.
2. Implement first/subsequent purchase plus reserve/consume/return preparation and simulation.
3. Implement submit/finalize/verify/recover plus pair-ledger/reservation projection indexing.
4. Rehearse public/restricted purchases and each booking-credit terminal path on Devnet with public evidence.
5. For the one-time coach bootstrap, update the program and generated client so recovery is a recorded non-signing address, then expose a bounded operator-only route that reconstructs and simulates the exact approved transaction server-side, collects only Tom's business signature, verifies that signature and the complete signer/instruction allowlist, adds only the platform-payer signature and submits once. The transaction must contain two deterministic Compute Budget instructions before the three business instructions so Phantom cannot inject an unreviewed priority fee at signing time. Keep this flow isolated from the marketplace UI.
6. Classify wallet-returned transaction validation failures separately from sponsor/RPC availability, expose only a bounded non-secret diagnostic in the development operator UI and retain exact signed bytes for safe recovery. This follow-up is required because repeated real Phantom submissions returned a fast generic HTTP 503 while finalized reads proved that nothing reached Devnet.

### Changes and rationale

- On 2026-10-05, the first real Phantom attempt exposed that requiring the recovery authority to co-sign initialization contradicted the confirmed one-user-facing-wallet product boundary and forced the operator to switch Phantom accounts. The user explicitly changed the bootstrap contract: Tom alone authorizes initialization, the configured recovery public address is stored without signing, and recovery remains mandatory only for a later wallet rotation. This requires a reviewed program upgrade before another Devnet bootstrap attempt; the expired two-wallet transaction created no accounts.
- After the single-wallet upgrade, two Tom-signed attempts and an expired exact-byte recheck all returned the same HTTP 503 in about 100 ms. Finalized account/signature reads proved that neither attempt reached Devnet. The generic result concealed whether Phantom changed the message, returned the wrong signer layout or produced an invalid/missing coach signature, so the bounded operator flow now needs explicit wallet-validation error codes before another real signature is requested.
- The bounded diagnostic identified `wallet-message-mismatch`. Phantom documents that it automatically adds Compute Budget priority-fee instructions to unsigned dapp transactions at signing time when those instructions are absent. The server must continue comparing exact reviewed bytes, so preparation now owns a 200,000-compute-unit limit and an explicit zero-micro-lamport price before the business instructions. This prevents wallet mutation, adds no priority fee, preserves the approved sponsor ceiling and remains appropriate for the Devnet rehearsal; a nonzero production priority-fee policy is intentionally outside this ticket.
- Added deterministic legacy-transaction preparation for first and later EURC offer purchases, booking-credit reservation, authorized return and coach consume. Preparation derives every program-derived address (PDA), associated token account and Anchor event authority from reviewed inputs; rejects stale offer/authority/ledger/reservation data; freezes the recent blockhash; and produces an exact JSON-safe Devnet approval summary.
- Added a bootstrap-only configuration and transaction boundary for the atomic CoachAuthority plus two-offer initialization. It accepts only a public recovery-authority address, enforces separation from the platform payer and coach, fixes nonce `0`/`1` public no-expiry offers at one/ten credits with consistent per-credit pricing, derives every PDA from the live local identity tuple and records explicitly that the bootstrap moves zero EURC.
- Added a server-only countersigning boundary. It decodes the wallet response, requires its compiled message to match the prepared message byte for byte, requires exactly the expected platform and business-authority signers, verifies the client/coach Ed25519 signature and only then adds the platform-payer signature. It returns a fully signed transaction and its deterministic fee-payer signature but does not broadcast it.
- Added strict runtime configuration parsing that pins `devnet`, HTTPS RPC endpoints and the reviewed `GvZdpXGX6N25xfHipgzh3Td3NZBkt7e36AougHi4v1MU` program identity while continuing to load the fee-sponsor secret only through the existing server-only source.
- Added strict Devnet RPC reads for the executable program, EURC mint and token accounts, coach authority, offer, pair ledger and reservation receipt. Every accepted program account is checked against the expected owner, fixed allocation and discriminator before decoding; token accounts are checked against the legacy SPL Token program, official EURC mint and expected wallet owner. Purchase preparation also rejects insufficient client EURC before a wallet prompt.
- Added actor-scoped persistence for exact prepared messages, simulations, blockhash lifetimes, deterministic signatures, ambiguous submissions and finalized evidence. Purchase attempts use a dedicated table because no booking exists before the first purchase; reserve/return/consume extend DEV0128's existing operation rows instead of creating a second booking state machine. Row-level security (RLS), security-definer functions, active-wallet checks and purchase rate limiting keep mutations behind the authorized server path.
- Added a server execution service and four same-origin authenticated routes for prepare, submit, recover and reject. The service performs RPC work outside database transactions, rechecks the actor before each write, stores the deterministic signature before broadcasting, treats a send error as ambiguous, and recovers only from finalized account state or safe blockhash expiry. Finalized purchase state updates the DEV0128 pair projection atomically with the purchase attempt; booking state uses DEV0128's existing verified transition.
- Added a browser adapter that converts the prepared base64 transaction to exact wallet bytes, passes the simulated context slot to the Wallet Standard signer and returns only the wallet-signed bytes to the bounded server submit route. It never gives the browser access to the platform sponsor or RPC credential.
- Added a development-only bootstrap operator route for the approved Tom fixture. The server gates it to Tom's exact local run, profile and ownership-proven wallet, reconstructs the atomic five-instruction message (two deterministic Compute Budget controls followed by the three business instructions) instead of trusting browser metadata, checks the three program accounts are absent before preparation, and simulates a fresh blockhash before the wallet prompt. The browser now collects only Tom's signature; submission verifies that Ed25519 signature and the exact two-signer/message allowlist before the platform payer adds only its own signature. A transient unavailable response keeps the exact signed bytes and exposes a recheck action instead of leaving the operator in a dead end.

### Decisions and deviations

Transaction messages use the legacy format for current Phantom compatibility. Purchase preparation always includes an idempotent coach EURC associated-token-account instruction so MovX can pay its rent if absent; the client EURC account remains the exact canonical account that supplies the purchase value. Approval fields that may exceed JavaScript's safe integer range cross the server/browser boundary as decimal strings. The submit route stores the deterministic signature before its one broadcast attempt, so a timeout is recovered by signature and finalized state instead of blindly resending.

The continuation keeps DEV0128's booking-operation rows as the durable business-operation boundary and adds only the prepared-message, blockhash-expiry and submission metadata that chain execution requires. Pass purchases receive a separate actor-scoped operation table because no booking exists before the first purchase. A server-only execution service owns RPC reads, account validation, simulation, countersigning, submission, finalized recovery and projection evidence; HTTP routes remain thin authenticated adapters and the browser receives only serializable approval/status data. This avoids a second booking state machine while keeping purchase and booking recovery idempotent.

The 2026-10-05 Devnet rehearsal assigns Tom's linked wallet `84g1vMUWb2umWbyEHSkaxpGtqyPDu3RsBnGzRsXfjuCt` as the coach and Hoang's linked wallet `3idZ8hddpfAZ1JWW3gmH7YD6yokUuFDb1Txem2H6kPFe` as the client. The user selected a `10 EURC` per-credit fixture price, so the public one-credit offer will freeze `10,000,000` base units and the ten-credit offer will freeze `100,000,000` base units. This is rehearsal configuration rather than a new product-wide price rule.

The initial coach bootstrap remains atomic: one legacy transaction initializes Tom's deterministic `CoachAuthority` and creates both public no-expiry offers. Tom is the only user-facing business signer; the distinct platform payer signs server-side for the authority/offer rent and fee, while the recovery authority is stored as a non-signing public address for later rotation. A failure in any instruction rolls back all three account creations, and no EURC moves during bootstrap. This replaces the earlier two-wallet initialization after the real Phantom attempt demonstrated its product and operational mismatch.

On 2026-10-05 the user moved application and database rehearsal back to local-only infrastructure because of Cloudflare issues while retaining the real Devnet program and test EURC for public-chain validation. The user later resumed the unsigned Devnet bootstrap sequence by linking Tom's wallet and configuring a dedicated recovery public address. No signature or submission is implied by that configuration or by simulation; each real transaction still requires a fresh reviewed summary and explicit approval.
