## Objective and context

Map a verified Supabase Web3 subject to exactly one prepared RepX Club profile and active demo dataset through idempotent server-side enrollment. An active demo dataset is the server-selected `demo_runs` database row containing one isolated set of prepared users and product records; it is not a fitness activity or login session. Add the durable wallet-binding contract plus identity repositories needed to prevent arbitrary persona selection, wallet reuse and cross-dataset claims.

DEV0038 authenticates control of a Phantom address but deliberately grants no application identity. This ticket owns the next boundary under the current [actors and authority contract](../../../docs/mvp-spec.md#3-actors-and-authority): controlled prepared enrollment and personal-wallet binding.

## Scope and non-goals

- In scope: define and migrate shared `wallet_bindings`; model active demo dataset, cluster, address, binding owner type, target and provenance; add Drizzle mappings and capability-owned identity/enrollment repositories; configure a server-only prepared roster that maps the verified wallet to Anna Klein and the active demo dataset; atomically and idempotently claim that seeded profile for the verified Supabase subject; enforce one wallet owner per dataset and one personal binding per prepared actor; expose a narrow enrollment/current-identity service and response contract; preserve an explicit wallet-disconnected state; test retries, races and wrong claims against real local PostgreSQL.
- Out of scope: an additional personal enrollment message or transaction signature; one-time `auth_challenges`, which DEV0041 will introduce for a distinct company wallet; Supabase provider sign-in/session implementation owned by DEV0038; private product-data row-level security and route guards owned by DEV0040; company-admin proof and company operations owned by DEV0041; open signup, persona picker, automatic wallet merging, production identity verification, payments, transaction signatures or chain state.

## Expected behavior and edge cases

After DEV0038 verifies the wallet and Supabase subject, the server privately maps that verified address to Anna Klein and the active demo dataset. The browser supplies no authoritative profile, dataset, role or owner type. On the first eligible request, one database transaction binds the Auth user, Anna's profile, her dataset participation record and personal wallet. A retry or simultaneous identical request returns the same identity instead of creating another binding. Supabase's verified wallet sign-in is the personal ownership proof; enrollment does not open a second Phantom prompt.

An unprepared address, a session whose verified wallet does not match the private roster, a different Auth user, an inactive dataset or participation record, or an already conflicting profile/wallet fails without partially claiming a profile. Concurrent claims converge on one matching result or a bounded conflict. A wallet already owned in the dataset cannot bind to another profile or organization; a profile or Auth user cannot silently acquire a second personal identity.

The user may disconnect Phantom at any time through the existing wallet control. Disconnecting does not sign out the Supabase session, delete Anna's profile or remove/reassign the durable wallet binding. The interface shows that the wallet is disconnected, and later wallet-signing or payment actions remain unavailable until the same bound wallet reconnects. Connecting a different wallet produces an explicit mismatch and never changes Anna's binding. Public wallet addresses and enrollment metadata may be stored; signatures, private keys and recovery phrases may not. Error responses use bounded application copy and do not leak the prepared roster or identify whether an arbitrary address is allowlisted.

### Locked implementation contracts — 2026-09-21

`app.wallet_bindings` has the following exact migration contract before implementation begins:

| Column                                | Contract                                                                                                                                                                                     |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                  | UUID primary key with `gen_random_uuid()` default.                                                                                                                                           |
| `run_id`                              | Required UUID referencing `app.demo_runs`; this identifies the isolated demo dataset.                                                                                                        |
| `cluster`                             | Required text; MVP check permits only `solana:devnet`.                                                                                                                                       |
| `wallet_address`                      | Required 32–44 character base58 text; server configuration additionally validates it with the installed Solana address codec.                                                                |
| `owner_type`                          | Required text, either `personal` or `organization`.                                                                                                                                          |
| `profile_id` / `organization_id`      | Mutually exclusive nullable targets. Personal rows require the profile and forbid the organization; organization rows do the reverse. Composite foreign keys keep either target in `run_id`. |
| `bound_by_auth_user_id`               | Required UUID referencing `auth.users`; records the verified Supabase subject that established the binding.                                                                                  |
| `provenance`                          | Required text; this MVP permits `prepared`.                                                                                                                                                  |
| `status`, `verified_at`, `revoked_at` | Status is `active` or `revoked`; `verified_at` is required; `revoked_at` is present exactly for revoked rows.                                                                                |
| `created_at`, `updated_at`            | Required audit timestamps with the shared update trigger.                                                                                                                                    |

Partial unique indexes enforce one active owner for `(run_id, cluster, wallet_address)`, one active personal wallet for `(run_id, profile_id)`, one active organization wallet for `(run_id, organization_id)`, and one active personal identity for `(run_id, bound_by_auth_user_id)`. A lookup index covers subject, status and run. Forced row-level security remains enabled with no general runtime read/write policy.

Two `SECURITY DEFINER` functions owned by the non-login `app_owner` role form the only DEV0039 runtime database surface: `app.enroll_prepared_personal_identity(...)` atomically claims a fixture profile and inserts or returns its exact active binding; `app.current_prepared_personal_identity(...)` reads that same exact mapping without mutation. Both require Auth subject, run slug, profile slug, cluster and wallet address supplied by trusted server code. Narrow `app_owner` policies activate only inside these functions through a transaction-local marker; direct `app_runtime` table access remains default-denied. Function execution is granted only to `app_runtime`, with public, `anon`, `authenticated` and `service_role` access revoked.

Server-only `PREPARED_PERSONAL_IDENTITIES_JSON` is a bounded JSON array of `{ walletAddress, profileSlug, demoRunSlug, cluster }`. Entries must contain valid Solana addresses, fixture-style slugs and `solana:devnet`; duplicate wallet or profile/run mappings fail configuration. The local ignored value maps the prepared Phantom address to `anna-klein` and `local-foundation-2030`. No private key or signature is stored.

`GET /api/auth/identity` reads the current mapping; `POST /api/auth/identity` performs idempotent enrollment. Both derive the subject/address from `verifiedAuthSession()`. POST accepts no identity body and requires the configured same origin. Responses are bounded `enrolled`, `not-enrolled`, `not-prepared`, `signed-out` or `unavailable` states with no unrestricted roster data. The sign-in screen automatically calls POST once for each verified subject/wallet and displays Anna after success; reload safely repeats it. Provider disconnect changes only live wallet availability, not the saved binding or Supabase session.

The migration is forward-only. Disposable local rollback uses `npm run db:reset`; any applied hosted correction uses a new migration rather than rewriting history. Local application testing provisions a loopback-only login inheriting `app_runtime`; hosted credentials remain environment-managed and are never committed.

### Decisions and deviations

The original plan required a separate one-time application challenge for personal enrollment. On 2026-09-21 the user chose the simpler flow: the successful DEV0038 Supabase wallet proof plus a private server mapping is sufficient to bind the prepared wallet to Anna Klein. `auth_challenges` moved to DEV0041 because a fresh proof is still necessary when an admin intentionally switches from a personal wallet to a different company wallet. The durable personal binding survives a provider disconnect; only live wallet-required authority becomes unavailable.

The implementation uses narrow database functions instead of granting a general application repository access to private identity tables. This keeps forced row-level security effective for direct runtime queries while allowing one reviewed transaction to lock/claim the prepared fixture and create or return its exact binding. Identical concurrent requests serialize on the profile lock and converge on the same row; a different subject reaches a bounded conflict.

No second message, transaction, balance or RPC operation was added. The server configuration error state is intentionally distinct from an unprepared wallet internally and becomes browser-safe `unavailable` copy; neither response exposes the roster. The HTTP POST accepts an empty body only so future browser fields cannot accidentally become identity authority.

Set server-only `DATABASE_URL` to that loopback login and set `PREPARED_PERSONAL_IDENTITIES_JSON` to the exact JSON array documented above. The ignored local value maps the user's prepared public address to `anna-klein` in `local-foundation-2030`; no key, recovery phrase or signature is stored. The variables have no `NEXT_PUBLIC_` prefix and are not returned by the API.

Responses contain only `status`, and for an enrolled identity the bounded profile, demo-run, role and wallet-binding snapshot. Disposable local rollback is `npm run db:reset` followed by `npm run db:runtime`; an applied hosted correction requires a new migration.

## Risks, limitations, and follow-ups

Prepared allowlisting is a bounded demo identity mechanism, not proof of one human or a production signup design. Wallet uniqueness does not prevent one person from owning multiple addresses. Reusing the verified Supabase session avoids a second proof-of-possession prompt; therefore session verification, private server-derived mapping, transaction atomicity and uniqueness constraints are the personal-enrollment security boundary.

DEV0041 must consume the shared exclusivity contract instead of adding a competing company-wallet table. DEV0040 must consume the verified identity result instead of trusting client profile/run claims.

The local runtime helper intentionally contains a fixed password only for the disposable loopback database on port 55322. It is not a hosted credential design. Product private-data policies remain out of scope until DEV0040; enrolling Anna does not yet authorize catalogue drafts, payments or any transaction.
