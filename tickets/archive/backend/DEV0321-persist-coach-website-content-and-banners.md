## Objective and context

The current coach record has a biography, disciplines and portrait but no structured website content or banner. Persist and safely project the optional M10 content so owner editing, cards and the website consume one authoritative public model.

Implement against the [M10 contract](../../../docs/mvp-spec.md#19-coach-marketplace-cards-and-personal-websites), especially [the relevant boundary](../../../docs/mvp-spec.md#192-public-content-and-template), [milestone](../../../docs/mvp-spec.md#12-delivery-milestones) and [acceptance matrix](../../../docs/mvp-spec.md#13-acceptance-matrix). The 17 October planning-only scope was authorized for implementation on 18 October 2026.

## Scope and non-goals

- In scope: Optional brand label, short introduction, approach, levels/focus, experience/qualifications, FAQs, safe external links and a distinct banner asset; owner revisions, draft/public visibility, bounded queries and migrations. Own banner processing, replacement/removal and cleanup through the application Storage boundary.
- Out of scope: Private price-term persistence (DEV0313), review persistence (DEV0314), owner/public page layouts, a gallery/video pipeline (DEV0297), private account fields, custom domains and username routing.

## Expected behavior and edge cases

Older profiles remain valid with every new field absent. Only the exact owner can mutate their content; pending/rejected applicants retain hidden drafts and publication still requires existing coach authority/locations. Public reads expose only the saved visible projection. Invalid URLs/text, stale revisions, missing banners and failed Storage/database writes recover without publishing partial content, leaking a private avatar or deleting a current replacement asset.

### Adopted implementation design — 18 October 2026, before source edits

- Keep this one reviewable persistence/API slice under DEV0321; no editor/card/page layout or pricing/review/username work. Use a separate optional `app.coach_website_content` row keyed by existing dataset/profile foreign key; no coach/name/location/avatar/portrait backfill or new publication requirement. One integer revision starts at zero when absent and covers content plus banner, with atomic compare-and-swap writes that lock the coach row. Pending/rejected owners may save private drafts; suspended/non-coach/other-owner/dataset contexts may not mutate.
- Content schema version 1 uses `brandLabel`, `introduction`, `approach`, `experience`, `focusLabels`, `faqs[{question,answer}]`, `links[{label,url}]`, all within section 19.2 limits. Missing optional fields normalize to empty strings/lists; reject unknown keys, markup/control text, unsupported versions and unsafe/non-HTTPS/credential URLs. Owner state includes revision/content/private preview URLs; public full state includes only saved eligible content and public banner routes; directory state includes only brand/introduction/focus and the card banner, never full FAQ/link/experience text or account/private image data. Current profiles retain compatible optional extension fields; owner API is independently consumable by DEV0315.
- Banner source: single-frame JPEG/PNG/WebP, at most 4 MiB, at most 24 million pixels/8,192 pixels per edge and minimum 320×120. Normalize server-side with rotation, centered 8:3 crop, stripped metadata, opaque neutral background, WebP quality 82; output `card` 800×300 (maximum 384 KiB) and `hero` 1,600×600 (maximum 1 MiB). Decode actual bytes, reject SVG/GIF/animation/malformed inputs; do not trust MIME or browser normalization. Gallery/video allowances remain deferred.
- Reuse the DEV0292 adapter with an additive `coach-banner` semantic scope mapped to a new private `coach-banners` bucket. Immutable flat owner-UUID/object-UUID.webp paths for each variant. Owner Storage rules permit eligible private draft preparation; anonymous/other-user reads require a currently referenced banner on a visible approved/demo coach in an active public dataset with a publishable primary venue. No public bucket/privileged-key download. Provider URLs/object paths stay out of DTOs; app image routes recheck references/visibility after download and use no-store, so hide/replacement revokes later reads.
- Owner `GET/PUT /api/coach/website` and `POST/DELETE /api/coach/website/banner` use bounded bodies, same-origin mutation checks and explicit expected revision (`If-Match` for banner). GET private/public variant routes serve only the current matching revision. Text and banner save separately and atomically; banner uploads both variants before attaching either. Upload/attach conflict cleans only new unreferenced variants; successful replacement/removal cleans old variants. Storage DELETE refuses any currently referenced object, protecting against ambiguous database outcomes and stale cleanup. Cleanup failure leaves an owner-scoped unreferenced orphan and a truthful successful current reference; document safe exact-path retry/operator reconciliation, without inventing an automatic retention job.
- Originals are never retained; current normalized variants remain until replaced/removed/owner deletion. Export/recovery uses the content row plus its two current private bucket objects; old orphan bytes are not public/export content. Additive migration follows 20261017001000 and is independently deployable before pricing/review migrations. Application rollback leaves optional data/bucket intact; destructive schema/bucket removal requires a separate export/retention operation.
- Read installed Next.js 16.3.8 Route Handler docs and Supabase JS/Storage 2.116.0 contracts; inspect Sharp 0.35.5 decode/resize/WebP types. Validate in isolated fresh/preserved-data databases, then apply only the reviewed additive migration to the existing local stack for real Auth/Storage/API proof. Never reset shared/hosted data. No hosted migration, commit or deployment is authorized by this step.

18 October concurrency review, before the affected SQL edit: serialize attachment and ordinary Storage deletion on the same owner-scoped database advisory lock. A pre-insert/update trigger takes that lock before the existing mutation function checks object existence (including its `INSERT … ON CONFLICT DO NOTHING` path); a volatile delete-policy helper takes it before rechecking current references. This closes the commit/cleanup race where an uncommitted attachment could otherwise be invisible to deletion. Keep the already locally applied first migration intact and add forward migration `20261018000200_coach_banner_cleanup_serialization.sql`; prove both acquisition orders in disposable database tests. PostgreSQL's documented [before-insert conflict behavior](https://www.postgresql.org/docs/16/sql-insert.html) informs this design. Also expose only a public-current boolean wrapper to anonymous Storage policy callers; revoke their ability to query the private current-reference predicate with `public_only=false`. No additional feature scope or permission is introduced.

### Changes and rationale

2026-10-18: Delivered the optional website content/banner backend on top of DEV0292. Existing coaches need no new required fields or backfill. Exact owners can save version-1 plain-text content and normalized banners, including hidden pending/rejected applicant drafts. An owner-scoped database lock serializes attachment and ordinary Storage deletion so cleanup cannot erase an in-flight/current attachment. A visibility change between directory reads drops the now-ineligible entry; failed reads remain unavailable. Full content, account identities, private avatar paths and hero/FAQ/link/experience data stay out of that directory extension. Existing layouts are unchanged; DEV0315/DEV0316/DEV0317 own their actual interfaces.

### Contracts, configuration, and operations

Schema-1 content keys: `brandLabel`, `introduction`, `approach`, `experience`, `focusLabels`, `faqs[{question,answer}]`, `links[{label,url}]`. Omitted optional keys become empty strings/lists; malformed values, unknown keys, markup/hidden controls, unsafe/non-HTTPS/credential URLs and unsupported schema versions fail. Bounds are section 19.2's 80/220/2,000/2,000 characters, eight 60-character labels, six 160/1,000-character FAQs and four 60-character labels/2,048-character HTTPS URLs. Character bounds count Unicode characters rather than UTF-16 code units.

Successful reads/mutations return 200 with `ready`/`saved`; invalid input 400, stale revision 409, signed-out owner 401, forbidden owner 403, absent public/current image 404 and unavailable infrastructure 503. Mutations return the saved owner website and optional `cleanupPending`. All application website/image responses are private/no-store with Cookie variance; image responses use WebP and nosniff. Banner Storage objects use cache age zero. Previous avatar/portrait behavior stays unchanged.

Persistence is an additive `(run_id,profile_id)` foreign-keyed optional table with canonical bounded JSON, one integer revision and two validated owner UUID paths. Only the actor-scoped mutation function can write through the restricted runtime. Banner insert/select permits eligible owners, including private applicant drafts; no Storage UPDATE policy or path overwrite is introduced. Anonymous Storage SELECT permits only current eligible public references. Ordinary DELETE locks/rechecks and refuses referenced objects. Public read functions return explicit narrow rows only to app_runtime; no new private account-field joins, dependencies or environment variables.

Migration order is `20261018000100` then `20261018000200`, independently before later pricing/review migrations. Both were applied only to the existing local stack using `supabase migration up --local` after isolated proof; no reset/seed/copy of retained local data or hosted migration. Deploy migrations before the new application; an older application may ignore the retained optional table/bucket on source rollback. Do not destructively drop the table/bucket as an application rollback: export the row plus current objects first under a separately reviewed retention operation.

Source originals are never retained. Current variants remain until replacement/removal/owner deletion; successful changes retire previous objects after reference commit. Cleanup is best effort: `cleanupPending` describes a successful save whose old-object cleanup needs retry. Reconcile exact owner-folder unreferenced objects against current database references and retry ordinary owner-scoped Storage deletion, whose lock/policy protects active references. Never delete `storage.objects` rows directly. Ineligible/deleted-owner orphan recovery requires an explicitly reviewed operator operation; this ticket adds no automatic sweeper/backup/export UI. UUID-only local recovery manifests/results contain no keys, tokens, passwords or image originals.
