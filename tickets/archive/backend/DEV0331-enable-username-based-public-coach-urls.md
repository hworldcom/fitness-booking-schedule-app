## Objective and context

Usernames are canonicalized, stored and unique under the current Account/registration implementation, but public coaches still resolve by a separate slug. The user now selected username-based public coach URLs. Implement the narrow public resolver, route and compatibility behavior in [section 19.6](../../../docs/mvp-spec.md#196-cards-username-urls-and-scheduling-compatibility), preserving internal coach/account identity and private account fields.

## Scope and non-goals

- In scope: reuse the existing canonical username as a public coach handle; `/@username` route/resolver; old `/coaches/[slug]` compatibility; owner-visible URL capability/result; narrowly needed Account username-write and claim-reservation integration; rename aliases/takeover defense; missing legacy handle recovery and fresh/upgrade migration/rollback evidence.
- Out of scope: username login, public athlete/account directory, a new canonical handle column, private-name exposure, full website/card layout or share metadata, custom domains, changing authentication authority and media decisions.

## Expected behavior and edge cases

Only an explicitly confirmed, visible approved/demo coach resolves publicly. Hidden, pending/rejected, non-coach, missing and unknown handles return indistinguishable public unavailable/not-found outcomes. A deliberately published coach handle is the sole planned disclosure exception to owner-only stored usernames; legal name, email and unrelated private details remain private.

Canonical usernames reuse current lowercase 3–30-character syntax/normalization and the existing Account uniqueness constraint. The `/@username` namespace avoids ambiguous collisions with old coach slugs. Legacy coaches without usernames keep old pages and receive an owner prompt to claim a handle; never derive one from a private name or silently unpublish them. When available, old slug links redirect to the same coach's current username URL with only safe date/section continuation.

Renaming retains previously published handles as aliases reserved to the same owner; no other signup or Account edit may take them. Keep the current username in its existing field, using a narrow published-handle registry only for public-route ownership/aliases. Claims/rename/alias registration are atomic across signup and Account writes. Clearing a published current handle requires an explicit replacement. Aliases recheck visibility and never restore a hidden coach. Handle changes do not alter coach IDs, bookings, review-pair identity, messages or existing group records.

### Adopted implementation boundaries — 2026-10-18

- Add `20261018000600_public_coach_usernames.sql`, with no handle backfill. A private registry stores published reservations only, not another canonical username. Deleted owners leave reserved tombstones; aliases cannot transfer to a different account.
- Serialize handle claims/confirmation through a short database advisory lock. An Account-table trigger guards both registration and Account writes, retains published aliases on rename and rejects clearing a published username. Existing unique-claim error mapping remains compatible; add explicit `username-required` feedback.
- Owner-only version-one capability contains username, Account revision and confirmation state. Explicit confirmation requires the displayed username/revision plus consent, checks current approved/demo coach authority and leaves visibility unchanged. Show this small control in the current Coach Profile; future DEV0315 consumes it rather than owning a missing prerequisite. A coach without a saved profile first saves that profile; missing usernames link to Account.
- The public resolver returns only visible coach slug/current public handle. A strict root `[handle]` route accepts only `@handle`, reuses the current public page renderer, and redirects aliases/case variants using temporary redirects so hiding/renaming cannot be bypassed by cached permanent redirects. Legacy redirects keep one valid ISO date and allowlisted `section=private-schedule`; arbitrary query values are discarded. Browser fragments do not reach the server.
- Public URL projections remain additive; internal slug/UUID arguments and booking/message/review authority remain unchanged. Extend public-page invalidation to the dynamic handle route. No new provider, environment variable or automatic account provisioning.

### Decisions and deviations

- The short advisory lock serializes canonical claims with first publication and alias reservation; existing unique-claim responses remain compatible. There is no global public Account lookup.
- A rejected clear initially surfaced PostgreSQL's aborted-transaction behavior when translated in JavaScript. The final migration keeps the original Account updater privately and translates only the named constraint inside a SQL exception boundary after rollback. Fresh/upgrade and real Account recovery now pass.
- The real browser found Next.js 16.3.8 supplies the leading at-sign as `%40`. Only that leading marker is normalized; encoded separators/repeated encoding remain rejected. Canonical comparison prevents redirect loops, and actual literal/encoded/case URLs pass.
- The initial cold endpoint compilation exceeded the first browser wait; later waits cover development compilation. A later test locator also matched Next's route-announcer alert; scoping it to the username fieldset fixed the test. Failed attempts cleaned up their exact fixtures. The final complete run passed.
- The root dynamic route brings two existing cross-page anchors into Next's internal-link lint match. Only those destinations were converted to `Link`; the full-document recovery reload remains unchanged.

### Contracts, configuration, and operations

`account_personal_details.username` remains the only current username. `coach_public_handles(username, profile_id, confirmed_at)` records only explicitly published reservations; deleting an owner sets its reference to null and preserves the reserved handle. Forced row-level security and revoked runtime table privileges protect the registry. PostgreSQL-owned security-definer functions have an empty search path and validate their bounded owner/public authority.

Owner `/api/coach/public-url` GET returns `{status:'ready',schemaVersion:1,username,revision,confirmed}` only for the current approved/demo coach with a saved profile. POST requires exact `{username,expectedRevision,consent:true}` JSON, same configured origin and at most 1,024 bytes. Stale confirmation returns 409, invalid 400, signed-out 401, forbidden 403 and unavailable 503. Owner results are private/no-store with Cookie variance. Confirmation leaves visibility unchanged. The capability is reusable by DEV0315; it contains no private legal name or other account fields.

Public coach projections optionally add `publicPath: '/@username'` after confirmation and current public eligibility. Omission means use the existing slug link. Directory paths are batched; repositories fail closed on ambiguous results. Both public pages are dynamic, use current visibility and return the same not-found presentation for hidden/unconfirmed/non-coach/unknown handles. Temporary redirects avoid a permanently cached alias bypass. The owner Account result adds `username-required` (409); signup alias collisions retain `username-taken` and roll back incomplete enrollment.

No dependency or environment variable was added. Local-only migration `20261018000600` and its ledger entry were installed in one transaction after isolated proof: every Account-row fingerprint matched, and the registry contained zero rows. No reset, reseed, existing coach opt-in, credential change or hosted operation occurred. Roll out the additive migration before the application. For rollback retain the schema/claim guard and all reservations; older successful Account/enrollment/slug readers remain compatible. Keep the route/resolver shim if any public handles have already been confirmed: deploying a router from before this feature would remove those new URLs. Never empty/drop the registry as rollback. Damage recovery uses the existing backup process or a reviewed forward correction; no new backup system is introduced.
