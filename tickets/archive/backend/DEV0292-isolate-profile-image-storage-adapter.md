## Objective and context

Contain Supabase Storage integration behind a narrow server-only adapter so future storage-provider changes do not require rewriting image validation, media permissions or profile behavior. This is a focused implementation follow-up to DEV0291's provider-coupling audit.

Use the current [architecture](../../../docs/mvp-spec.md#6-application-and-infrastructure-boundaries), [identity/privacy](../../../docs/mvp-spec.md#8-identity-data-and-demo-integrity), [definition of done](../../../docs/mvp-spec.md#11-definition-of-done), [milestones](../../../docs/mvp-spec.md#12-delivery-milestones) and [acceptance matrix](../../../docs/mvp-spec.md#13-acceptance-matrix). These are linked independent records, not a child-ticket hierarchy or additional COR0027 members.

## Scope and non-goals

In scope: inventory upload/read/remove/URL handling across profile and authorized message media, define typed application-owned Storage results, extract the concrete Supabase implementation, keep credential/session handling inside it and add meaningful contract/failure/privacy regressions. Out of scope: changing providers, copying buckets, new media/profile features, Auth redesign, rewriting database authority or performing backup/restore.

## Expected behavior and edge cases

Application services retain normalization, private-avatar/public-portrait rules, reference attachment and authorized actor checks. The adapter performs provider I/O and translates failures into bounded application results. Preserve current routes, content types, immutable object naming, cache/privacy headers, missing-image fallback and owner-scoped credentials. An adapter must not bypass Storage row-level security through a privileged key. Failed upload never attaches a missing object; failed cleanup must retain existing truthful behavior.

## Assumptions, decisions, and dependencies

Existing image service calls client.storage directly and receives Auth client configuration; first inventory all related reads before choosing the final interface. Keep request/session scope and existing profile/booking/connection/message media grants. DEV0286 owns Auth gateways; this ticket owns Storage only. Existing provider-specific URL compatibility and SQL policies remain explicit; no claim of a universal interchangeable storage system.

Add a small shared application upload/attach workflow to preserve and meaningfully test ordering: failed upload cannot attach, lost authority/conflict removes only the unattached new object, and failed old-object cleanup does not undo a successful reference update. Concrete provider details stay outside that workflow.

## Implementation record

### Changes and rationale

2026-10-17–18: Replaced direct Storage calls and provider-origin reads in image services and public projections with a server-only application interface. `ProfileImageStorage` exposes semantic account-avatar/coach-portrait scopes, upload/download/remove and public-portrait URL projection; all failures return only `unavailable`. The concrete Supabase adapter obtains the existing cookie-backed public-key client for each operation, never caches an actor/session/client and does not use admin credentials. Existing private reference lookups and the connection's post-download grant recheck remain application authority.

Upload normalization, immutable object names and atomic reference writes stay in the application. A shared store/attach workflow runs upload before any reference mutation, removes only the new unattached object after conflict/access loss, and treats old-object removal as best-effort after success. Private endpoints, source dimensions/type, content/cache headers, public URL shape/version, missing/unavailable outcomes and identity/ref data are preserved. Public URL construction is no longer mixed into the browser/shared image contract or six actor/repository/media projection consumers.

Added provider-boundary enforcement, installed-SDK HTTP behavior/failure tests, upload/reference ordering checks and a bounded local password-authenticated rehearsal. The older profile-image script still assumes retired email-code UI, so this ticket establishes `npm run test:profile-storage` rather than changing unrelated Auth work. README documents the actual command and section 6.1 reports the delivered boundary honestly. No provider/bucket/policy/schema migration or new image feature was introduced.

### Decisions and deviations

2026-10-17: Choose semantic storage scopes, request-scoped provider client creation and a synchronous provider-owned portrait URL projection so public reads do not require an authenticated Storage download. Preserve legacy URL shape and domain allowlist explicitly. Existing Auth core is locally implemented; its hosted/Google completion is not needed to preserve this current cookie-backed client. The legacy profile-image rehearsal still expects email-code login; use a bounded current-password local smoke instead of altering unrelated ongoing Auth rehearsals.

2026-10-17: Preserve existing providers and application authority while reducing specific coupling. Keep disaster recovery separate from password reset and retained-volume migration repair. No runtime deviation; implementation choices remain scoped to this record.

### Contracts, configuration, and operations

Internal interface: `ProfileImageObject {scope: account-avatar | coach-portrait, path}`; upload/remove return `{status: ready | unavailable}`; download returns ready ArrayBuffer-backed byte data or unavailable; public portrait projection consumes the existing fixture/storage reference and returns a URL or null. Scope-to-bucket mapping and configured origin are adapter-private. Credentials still come only from the current request's existing Auth client/public configuration; no caller can request an elevated key through this interface.

No HTTP route/payload, database schema/migration, provider/bucket/policy, image quota/normalization, dependency or environment changes. No historical reference or object migration. Package adds only the documented local test command. Rollback is an application-source rollback with compatible internal callers; retained data/objects need no rollback or conversion. Existing provider-specific SQL policies, two buckets, UUID object layout and domain URL allowlist remain explicit compatibility obligations, so this is not a universal provider swap. DEV0321 may later extend reviewed scopes/policies for banners; this refactor does not provision that feature. No secrets are recorded.
