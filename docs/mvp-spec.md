# MovX Club — Scheduling-only MVP specification

Last updated: 14 October 2026.

MovX is a focused scheduling product for martial-arts coaching. Guests discover platform-approved coaches or clearly labelled fictional demo coaches and their real published availability. Email-authenticated athletes request one capacity-one private session, and the coach confirms one athlete before a booking exists. Approved coaches manage their public profile, training locations, location-aware recurring one-hour availability, request queue and booked schedule.

This standalone project intentionally has no blockchain, wallet, token, pass, credit, payment, group-funding, event-marketplace, follow, post or feed behavior. Completed and archived records for those features are historical evidence only and do not define current product behavior. Solana hackathon development belongs to the separate `fitness-booking-social-app` repository.

## 1. Product status and document authority

This document is the single current product contract for the standalone scheduling repository. It defines target behavior and does not claim every target is already implemented.

The repository contains reusable Next.js, Supabase/PostgreSQL, email identity, coach profile/location, list-first discovery, recurring availability, responsive calendar and Vercel foundations. Direct scheduling-only booking and the removal of obsolete runtime were delivered under completed [COR0011](../tickets/archive/organisatory/COR0011-scheduling-only-product.md). The approval-only request target defined here, including separate coach/athlete interfaces and atomic conversion of one accepted request into the confirmed booking, is delivered under completed [COR0016](../tickets/archive/organisatory/COR0016-coach-confirmed-booking-requests.md).

Tickets record implementation scope and evidence; they do not override this specification.

Athlete website terminology is delivered under [DEV0220](../tickets/archive/frontend/DEV0220-use-athlete-website-terminology.md). Mutual coach–athlete connections remain an adopted target under [COR0020](../tickets/current/organisatory/COR0020-athlete-terminology-and-connections.md); connection persistence and interfaces are not delivered yet. An athlete is an account acting as the training participant, previously called a client. Existing internal `client` identifiers, database fields and compatible sign-in values keep their technical meaning; this vocabulary change adds no new role or authority. A coach may also participate as an athlete through the same account.
The disconnect/reconnect shared-history target is clarified by [DEV0230](../tickets/archive/organisatory/DEV0230-adopt-reconnection-history-recovery.md). Conversations remain separately planned under [COR0015](../tickets/current/organisatory/COR0015-session-notes-and-training-plans.md); neither connection nor conversation runtime is delivered by that contract amendment.

Archived tickets remain immutable history. [DEV0140](../tickets/archive/organisatory/DEV0140-adopt-scheduling-only-contract.md) records the decision to create this focused product split.

### Proposed implementation defaults

The following are implementation defaults rather than additional user decisions:

- Availability is materialized as dated one-hour occurrences for a rolling seven-day window from recurring weekly rules.
- Repeating a request while the same athlete already has an active attempt for that occurrence returns the existing request rather than creating a duplicate.
- Expiry may be reconciled transactionally during participant/public reads and request mutations for the first release; no background scheduler is required by the product contract.
- A coach or athlete cancellation records who cancelled and when; P0 does not require a reason field or notification delivery.
- Historical migrations may retain unused wallet/payment/event tables for safe forward compatibility. Current code does not read or expose them.
- Referenced training locations are deactivated rather than destructively deleted; changing the primary location is one atomic replacement.
- A location selected from optional provider search becomes bounded coach-owned profile data. It does not silently create a global gym or point-of-interest catalogue record.
- The location-aware calendar uses stable text cues in addition to color so every assigned venue remains understandable without color perception.
- Connection requests may be declined by the recipient or withdrawn by the sender; unsuccessful attempts and removed connections retain bounded lifecycle evidence. Reconnection requires a fresh request and explicit acceptance with current eligibility. Exact retry/resend bounds are recorded by the persistence ticket before implementation.
- Crossed connection requests recover the existing pending request and require explicit recipient acceptance; sending never silently accepts. One coach-profile/athlete-profile pair is distinct from the reverse teaching relationship when both accounts coach. Self and cross-dataset pairs are invalid.
- Approved/demo coaches may create or accept new connections with qualifying athletes even when their coach profile is hidden; suspended coaches retain existing relationship reads/removal and pending decline/withdrawal but create or accept no new connection. Discovery and rebooking still obey their existing visibility/approval rules.
- My coaches is reachable within My sessions, and My athletes within Coach workspace → Bookings; pending requests remain separate from accepted lists. These placements preserve existing primary navigation. Connection status is application-only, with no email or push promise.

## 3. Actors and authority

### Guest

A guest can browse the public story, coach list, coach profiles, confirmed locations and future open times. A guest cannot submit a request or mutate schedule state.

<a id="client"></a>

### Athlete

An athlete has a verified email-backed MovX account and application profile. The athlete can request one eligible future occurrence with another coach, view only their own pending-request status, upcoming confirmed sessions and retained history in `My sessions`, withdraw their own pending request, cancel their own future confirmed booking and optionally manage a private account avatar. A terminal unsuccessful attempt does not consume capacity and may be followed by a new attempt while that occurrence remains eligible. Ordinary athletes plus pending and rejected coach applicants receive `My sessions` as their private primary-navigation destination and no `Coach workspace` item. An account avatar does not become public coach media merely because the account later applies to coach.

### Coach

A coach retains athlete capability, so approved and fictional demo coaches keep `My sessions` and additionally receive `Coach workspace` in desktop and mobile navigation. Their main `Profile` item opens coach Profile by default, while the bottom-left and upper-right account controls continue to open the personal account Profile. Coach Profile, Schedule and Bookings share one paper-background coach-workspace heading with a truthful publication summary and one Profile-first sub-navigation at a stable position before the active view's content; Schedule contains location-aware recurring availability and dated capacity status, while Bookings alone contains the private paginated request queue, detailed booked schedule, authorized athlete identity/avatar and booking actions. After platform approval, the owner can publish their coach profile, manage multiple confirmed training locations, select one active primary location, optionally manage a separate public coach portrait, assign recurring availability to actual locations, accept or decline pending requests, close one unavailable occurrence, inspect confirmed bookings, cancel a future confirmed booking and mark an elapsed confirmed booking completed. A pending or rejected applicant may prepare a private draft but has no public coach or scheduling authority. A suspended coach receives the same two private destinations, with bounded Bookings access needed to resolve existing confirmed sessions, but accepts no pending request, receives no new request and makes no public-media change. A coach cannot see unrelated requests, athlete bookings or private identity data.

### Platform reviewer

Until the internal admin panel exists, an authorized operator uses a guarded owner-only command to approve, reject or suspend an exact coach application. Every decision records the expected prior state, reviewer/source, bounded reason, verification-policy version and immutable audit event. Ordinary application/runtime roles cannot review applications or grant coach authority.

### MovX service

MovX verifies the Supabase session, establishes transaction-local actor context, enforces row-level authorization and performs bounded database mutations. It does not invent coaches, availability, requests or bookings when configuration/database access is unavailable.

## 4. Primary user flows

### 4.1 Register as an athlete or apply to coach

1. A visitor requests a one-time email code and verifies it through Supabase Auth.
2. MovX creates or restores the same minimal application profile.
3. The visitor follows the `Find a coach` path and can use athlete behavior immediately, or follows `Become a coach` and submits a coach application.
4. A pending applicant may prepare a hidden coach-profile draft but cannot publish availability or receive booking requests.
5. A guarded platform review approves, rejects or suspends the application atomically with audit evidence.
6. Approval unlocks coach publication and scheduling without removing athlete capability, and primary navigation adds `Coach workspace` alongside `My sessions`. Approval does not automatically make the profile visible.
7. The account may manage a private avatar from Account Profile. An approved coach separately chooses whether to add a public portrait to the coach profile.

### 4.2 Discover a coach and time

1. A guest opens Home and can immediately submit discipline and location filters or inspect a bounded alphabetical preview read from the authoritative public coach directory. Home omits the coach/focus field for now; explanation and coach-application content follow discovery rather than displacing it.
2. Home submits discipline and location values to Explore through a native GET form; its discipline links carry no coach/focus query. Explore retains normalized `q`, discipline and location search and compatible bookmarked URLs. Unsupported date, weekly availability, proximity, price, rating and review controls do not appear.
3. Explore returns the complete server-backed filtered list of visible coaches. Desktop places that list beside the primary-location map; mobile defaults to list and uses canonical `view=list|map` state without losing filters or browser navigation.
4. OpenFreeMap-backed discovery shows each visible coach once at that coach's confirmed active primary location without an application map key. Map failure returns or retains the complete list and profile links.
5. The primary marker describes the coach's public training base, not live presence or today's venue. Explore has no date selector and keeps the coach visible when there is no open time today; any today summary labels the actual occurrence locations or reports `No availability today`.
6. A coach profile shows bounded public details, an optional public portrait, every confirmed active training location with the primary one labelled, and future open dated one-hour occurrences grouped or labelled by actual location. One provider-neutral map fits all active locations; distinct matching marker/list colors and numeric labels aid comparison without replacing names and addresses, and map failure leaves the list usable. Missing portraits use initials rather than a fabricated image.
7. No placeholder coach, location or time is shown when persistent directory or availability data is empty or unavailable.

### 4.3 Request a private session

1. A signed-in athlete selects one open future occurrence belonging to another visible coach. No fixed minimum-notice interval applies.
2. One authorized database operation rechecks actor/dataset/coach/time/status boundaries and creates or recovers that athlete's active pending request. It sets the decision deadline to the earlier of 12 hours after the database submission time or occurrence start, and leaves the occurrence open.
3. The athlete sees `Request saved`, `Awaiting coach confirmation`, `This session is not confirmed yet` and the concrete decision deadline in `Europe/Berlin`. The response contains no other candidate identity, count or status.
4. Other eligible athletes may independently request the same occurrence. No pending request holds capacity, and coach-facing result sets remain bounded through pagination even though no candidate cap applies.
5. Reload derives the same active request from PostgreSQL. The athlete can withdraw it; after withdrawal, expiry, coach decline or non-selection, the athlete may create a new attempt only if the occurrence is still open and future.

### 4.4 Decide booking requests

1. The owning coach opens the private paginated request queue in Bookings and reviews requests grouped by occurrence.
2. The coach may decline one pending request, accept one pending request or close that one occurrence when no longer available.
3. Acceptance locks the occurrence and active requests together, creates one confirmed capacity-one booking for the selected athlete, marks the occurrence booked, accepts that request and closes every other pending request as not selected in one transaction. Those athletes see neutral `Not confirmed` or `Request closed` presentation rather than competition-oriented wording.
4. Decline terminalizes only that attempt. It leaves the occurrence and other pending requests open, and the same athlete may submit another eligible attempt.
5. Closing the occurrence marks it withdrawn and closes all pending requests as unavailable in one transaction. It does not edit the recurring availability rule or create a booking.
6. A request that reaches its decision deadline expires without consuming capacity. That deadline is normally 12 hours after submission but is capped at occurrence start for a late request. Concurrent accept/decline/withdraw/expire/close operations resolve to one authoritative idempotent outcome.

### 4.5 Cancel a booking

1. The owning athlete or coach selects a future confirmed booking.
2. One authorized operation records the cancellation actor/time and reopens the future occurrence.
3. Repeating the same cancellation returns the same terminal outcome; a different or unauthorized actor cannot mutate it. Reopening the occurrence never revives earlier request attempts, so athletes must submit new requests while it remains eligible.

### 4.6 Complete a session

1. After the scheduled start, the owning coach can mark a confirmed booking completed.
2. Completion is terminal and idempotent. Athletes and unrelated coaches cannot complete it.
3. P0 does not claim independent attendance proof or resolve service disputes.

### 4.7 Manage locations and publish availability

1. An approved coach adds or confirms one or more provider-neutral training locations and selects exactly one active location as primary before publishing the profile.
2. The coach chooses an active location in Schedule, assigns one or more weekly cells to it locally and may switch locations to continue composing the complete working-week draft.
3. One explicit authorized save validates ownership, active-location state, the expected baseline and per-coach time overlap before replacing the complete recurring rule set and synchronizing dated occurrences once.
4. Every dated occurrence copies the actual assigned location snapshot. Changing the primary location never moves an existing occurrence or booking.
5. Deactivating a location stops new availability there, withdraws eligible future open occurrences and closes their pending requests while preserving booked and terminal history.

### 4.8 Participate as an athlete

Participant-facing website labels use athlete terminology consistently. Personal account labels, onboarding paths, public explanations and coach request/booking rows reflect that vocabulary. Coaches retain My sessions for the sessions they request as athletes and Coach workspace for the sessions they teach; identity and authorization remain unchanged.

### 4.9 Connect after a confirmed session

1. A coach and athlete who share at least one confirmed or completed booking can open Connect from their authorized session context. A pending booking request or cancelled-only history is insufficient.
2. Either participant sends a connection request. The server verifies their exact pair and qualifying booking state; sending creates no accepted relationship.
3. The recipient explicitly accepts or declines; the sender may withdraw. Acceptance rechecks that at least one shared booking is still confirmed or completed, so cancellation can invalidate a pending request unless another qualifying session remains.
4. Acceptance adds one pair to My coaches and My athletes, separately from incoming/outgoing requests and booking history. More confirmed sessions do not create duplicate connections.
5. The coach sees only that connected athlete's name, current photo or initials and pair-owned session history. The athlete sees the retained coach identity, its available public portrait and shared sessions; public-profile/rebooking shortcuts obey existing visibility and approval.
6. An accepted connection persists across cancellation/completion. Either participant may disconnect; removal revokes connection-derived data/media access without deleting or resetting requests, bookings or retained shared content. Exact participants retain their independent request/session permissions.
7. Reconnecting requires a fresh request and explicit acceptance with current eligibility. The relationship history view restores all retained shared requests and bookings, including declined, withdrawn, expired and not-selected requests and cancelled sessions. Conversations, shared plans and shared notes, when COR0015 is delivered, return through their original request/booking context. The selected request and its resulting booking represent one continuing conversation, not duplicated threads; terminal/cancelled content remains read-only. Coach-private notes never enter the shared history.

## 5. Scheduling state model

### Application profile

One profile belongs to one verified Supabase Auth identity inside a dataset. It stores the bounded display identity used for authorization and presentation.

### Coach application and review

One current coach application belongs to one application profile. Absence means not applied; submitted applications move through `pending`, `approved`, `rejected` or `suspended`. Review events are append-only evidence of platform decisions. Historical self-service activation may remain stored for continuity but grants no current coach authority.

### Coach profile and training locations

One owner-scoped coach profile contains public name, slug, biography, disciplines, visibility, one scheduling timezone and an optional public portrait reference. It owns one or more confirmed provider-neutral training-location records; each record has stable identity, kind, public label, coordinates, provenance and active/inactive lifecycle, and may optionally reference a reviewed gym. Exactly one active location is primary while the profile is visible. That primary record supplies the coach's single Explore marker and public training-base label, but it does not establish live presence, choose an occurrence venue or grant gym/account authority.

Pending/rejected applicants may keep only a private draft; a user-created profile enters public discovery only while its application is approved, its owner selects visible and one confirmed active primary location exists. Provider-search selection stores only the bounded coach-owned location the coach explicitly confirms and does not populate a global point-of-interest catalogue. Referenced locations are deactivated rather than destructively deleted so scheduling history remains resolvable.

### Profile images

Image bytes live in Supabase Storage rather than PostgreSQL or the Vercel deployment filesystem. PostgreSQL stores only bounded source/path/version metadata. Private account avatars and public coach portraits use separate storage/access contracts; attaching an image never grants account or coach authority. Signed-in account presentation—including the desktop bottom-left account control, upper-right header control and Profile—prefers its private avatar and otherwise may display the owner's already-public coach portrait as a read-only fallback. A regular account therefore shows its private avatar or initials, while a coach can additionally fall back to the public portrait. Athlete `My sessions` cards may project the booked coach's current public portrait and link its complete visible identity to the existing public coach profile; a missing, removed or unreadable portrait retains initials. The owning coach may retrieve a request participant's current private avatar through a request-scoped authenticated application route for as long as that request record is retained, including terminal recent-request history. The owning coach of a confirmed booking may separately retrieve that booking athlete's current private avatar through a booking-scoped route while the booking remains confirmed. Public callers, athletes and unrelated coaches receive no image bytes, and the browser never receives the private Storage object path. These fallbacks and bounded reads do not copy media between buckets or change which endpoint removes each image.

JPEG, PNG and WebP source selections are accepted for the first release. The browser corrects orientation, square-crops and downsizes before upload; the server treats that output as untrusted, validates and re-encodes one canonical 512 × 512 WebP at quality 82, strips metadata and retains no original. The selected source is limited to 8 MiB and the canonical upload to 512 KiB. Replacement writes a new immutable object path before retiring the prior owned object so content-delivery-network caches do not retain an overwritten image. Removal restores the initials fallback.

### Coach–athlete connection

A connection is a private lasting relationship for one coach-profile/athlete-profile pair within the same dataset. A request records the sender and recipient; only its recipient accepts or declines, and only its sender withdraws. Its lifecycle is `Pending → Accepted`, `Pending → Declined` or `Pending → Withdrawn`; either accepted participant may transition `Accepted → Removed`. A fresh request may reconnect an eligible pair after a terminal outcome, while old attempts remain terminal. Crossed sends return the existing pending request rather than implying consent.

Pair identity, participant IDs, request/attempt identity, lifecycle state, creation/update/decision timestamps and decision/removal actor are the minimum authority data. PostgreSQL enforces one active pending/accepted pair and rechecks a shared confirmed/completed booking at sending and acceptance. A later cancellation never removes an already accepted connection. A different teaching direction between two coach accounts is a distinct pair; self and cross-dataset pairs fail closed.

Accepted projections contain only participant identity, bounded current presentation and sessions shared by that exact pair. The coach receives an authenticated connection-scoped opaque URL for the athlete's private avatar. Pending/declined/withdrawn/removed connections grant no new private-media or session-history access. Removal revokes the connection permission on the next read, with caching that cannot preserve former access; separate request/booking permissions remain intact. Goals, biographies, public athlete profiles, general messaging and notifications are not added.

Disconnecting is a relationship transition, not a content-deletion operation. A fresh accepted attempt for the same pair restores access to a complete bounded history view of retained shared requests/bookings and, after COR0015 delivery, their conversations, shared plans and shared notes. Retrieval may be paginated but must permit access to all retained records rather than silently dropping older history. Each request/booking and conversation keeps its original stable identifier, authors, timestamps, status and permissions; reconnection neither reopens terminal records nor copies content into a new request or booking. Independent participant access survives disconnection. Recovery includes unsuccessful request threads and cancelled-session content, excludes coach-private and unrelated content, and does not bypass qualifying-session/coach eligibility or future separately adopted account-retention policy.

### Recurring availability and dated occurrence

A recurring weekly rule belongs to exactly one active training location owned by the same coach and creates deterministic dated one-hour occurrences in the coach's single scheduling timezone. One weekday/time cell belongs to at most one location. An occurrence is `open`, `booked` or `withdrawn`, carries the immutable snapshot of the rule's actual location and belongs to exactly one coach. An open occurrence may have multiple independent pending requests without being held or booked. Overlapping rules/occurrences are rejected across all of the coach's locations. Changing which location is primary does not change a rule or occurrence.

### Booking request

A booking request is one athlete's attempt to receive coach confirmation for one occurrence. The same athlete has at most one active request for that occurrence, while terminal attempts remain immutable history and do not prevent a later eligible attempt. There is no per-occurrence candidate cap; private coach queries use bounded pagination. Its lifecycle is:

```text
Pending -> Accepted
Pending -> Declined
Pending -> Withdrawn
Pending -> Expired
Pending -> Not selected
Pending -> Occurrence closed
```

`Accepted` creates and links exactly one confirmed booking. Accepting one request makes every other pending request for that occurrence internally `Not selected`; closing or otherwise withdrawing the occurrence makes them `Occurrence closed`. Athlete presentation uses neutral `Not confirmed`, `Request closed` or `Session unavailable` language and never describes competition. All other terminal outcomes consume no capacity. Minimum request fields are request/attempt ID, occurrence/coach/athlete IDs, scheduled time and actual location snapshot, status, creation/update timestamps, decision deadline capped at occurrence start, decision actor/time and an optional accepted-booking ID. The athlete projection contains only that athlete's attempt and never exposes other request identifiers, identity, count, status or content.

### Private booking

A private booking is created only when the owning coach accepts a pending request and binds that occurrence, coach profile and selected athlete profile. Its lifecycle is:

```text
Confirmed -> Cancelled
Confirmed -> Completed
```

Minimum projection fields are booking ID, occurrence ID, coach/athlete IDs, scheduled start/end, actual occurrence-location snapshot, status, creation/update timestamps, cancellation actor/time and completion time. It contains no wallet, pass, credit, token, price, transaction signature or chain reference.

## 6. Application and infrastructure boundaries

- Browser code receives only public configuration and bounded projections.
- Next.js server code verifies sessions and owns authorization/database calls.
- Supabase Auth establishes email identity; editable profile fields do not establish authority.
- PostgreSQL is authoritative for profiles, coach applications/reviews, locations, availability, occurrences, booking requests and confirmed bookings.
- Supabase Storage owns normalized image objects. Private account-avatar access and public coach-portrait delivery remain separate; PostgreSQL stores only their bounded references.
- The location module isolates MapLibre/OpenFreeMap rendering and optional Geoapify gym/place search; stored provider-neutral coach-location and occurrence snapshots remain application authority, and legacy provider snapshots remain readable without calling their former provider. The module does not decide primary status, schedule assignment or coach authority.
- Vercel runs the native Next.js application. Hosted secrets are encrypted server-only environment values.
- Historical blockchain/social tables may remain in migration history but are not current runtime dependencies.

## 7. Requests, booking and recovery

Request creation, withdrawal, decline, expiry, acceptance, occurrence closure, booking cancellation and completion are atomic database operations with stable UUID identity and explicit actor context. Start/deadline checks use database instants, not the browser clock. The active-booking uniqueness rule prevents double confirmation even when several requests exist or coach actions race.

A request is eligible only when the occurrence is open, belongs to another visible coach and starts after the database statement time. No fixed minimum notice applies because only coach acceptance assigns capacity. Creation fixes its deadline at `least(created_at + 12 hours, scheduled_start_at)`, so a late request never remains pending after training begins. The Berlin-only interface renders these instants in `Europe/Berlin`, including daylight-saving changes, without changing stored authority.

A repeated same-athlete submission returns that athlete's active request. A terminal unsuccessful attempt—withdrawn, expired, declined, not selected or closed with the occurrence—remains history but permits a new attempt while the occurrence is still open and eligible. No candidate cap applies. Coach request queries are paginated, and athlete projections never contain another request or aggregate candidate count.

Acceptance locks the occurrence and relevant requests in deterministic order, creates one confirmed booking, marks the selected request accepted and occurrence booked, and closes every other pending request as not selected. Coach occurrence closure uses the same concurrency boundary to withdraw that occurrence and close its pending requests without selecting anyone. Decline closes one attempt; withdrawal belongs only to its requesting athlete; bounded reconciliation expires overdue requests. Every mutation returns the state that actually won rather than false success.

Cancellation locks the confirmed booking/occurrence together, records the authorized actor and reopens only a future occurrence. It does not revive earlier request attempts; interested athletes submit new requests if the reopened occurrence is still open and future. Completion locks the booking and requires the owning coach plus an elapsed scheduled start. Terminal request and booking transitions are idempotent and cannot be reversed.

Connection send/accept operations recheck exact participants, current coach capability and a shared confirmed/completed booking inside the database mutation. Booking cancellation and connection acceptance must serialize their qualifying-state check so a race cannot accept a pair that lacks a qualifying booking at the winning acceptance instant. Duplicate/crossed sends, replayed decisions and accept/remove races return the authoritative attempt/pair state; stale request identifiers cannot accept a newer attempt. Connection actions never alter session capacity, booking state or request eligibility.

- Explore keeps every otherwise visible coach on the map at the primary location regardless of today's availability. It has no date selector in this delivery; today's actual session venues or `No availability today` are presentation details and never move or remove the primary marker.

Inactive history is omitted, text identifies every place without relying on color, and map failure does not remove or disable the list or schedule.
- A pending or rejected applicant may edit only a private coach-profile draft. Only an approved coach owner publishes that profile, manages public training locations or edits recurring availability.
- A verified account owner may replace/remove only their private account avatar. Only an approved coach owner may replace/remove their separately public coach portrait; image ownership never substitutes for coach approval.
- A visible coach has exactly one confirmed active primary location. Replacing primary is atomic, and the current primary cannot be deactivated without a valid replacement.
- A coach composes recurring availability as a local location-aware working-week draft: the selected active location is assigned to empty cells, every selected cell exposes its location through text as well as any color cue, and one explicit authorized save replaces the complete rule set and synchronizes dated occurrences once.
- Deactivating a location removes its active recurring rules, withdraws eligible future open occurrences and closes their pending requests without moving or deleting booked/terminal snapshots.
- A suspended coach is removed from discovery, cannot publish availability, receives no new requests and cannot accept an existing pending request; pending requests close as unavailable while existing confirmed-booking history and bounded terminal actions remain available to the owning parties.
- Only a verified signed-in athlete submits or withdraws their own booking request, and never against their own coach profile.
- Every occurrence uses coach approval. An athlete request leaves it open; no instant-booking or coach booking-mode setting exists.
- Request creation remains available until training starts. Each request expires at the earlier of 12 hours after submission or occurrence start. Eligibility uses database instants and the first-release interface displays deadlines in `Europe/Berlin`.
- Only the occurrence's owning coach accepts or declines its pending requests. Acceptance confirms exactly one booking and atomically closes the rest; decline leaves the occurrence and other requests open.
- The owning coach may close one open occurrence without selecting a request. Closure withdraws only that occurrence, closes its pending requests and does not edit its recurring rule.
- An athlete may submit a new attempt after an unsuccessful terminal outcome while the occurrence remains open and future.
- Only the booking athlete or coach cancels a future confirmed booking.
- Only the booking coach completes an elapsed confirmed booking.
- Unrelated accounts receive no booking identity or mutation capability.
- Removing a recurring rule does not silently delete terminal booking history.
- Athlete vocabulary describes participation without granting coach capabilities or changing existing identity/data identifiers.
- Only exact pair participants may send connection requests; at sending and acceptance the pair must share a confirmed/completed booking. Only the recipient accepts/declines, only the sender withdraws, and either accepted participant removes.
- My coaches and My athletes contain accepted relationships, with pending requests separately labelled. An accepted relationship survives cancellation/completion; removal leaves history and session-specific participant permissions intact.
- Connection-scoped private athlete identity/photo and history reads require current acceptance and exact coach/pair scope. Connections never bypass public-profile visibility, coach approval or booking eligibility.

## 10. Security and failure invariants

- Actor context is derived from a verified session and set transaction-locally.
- Direct table permissions remain least privilege; security-definer functions validate actor context and exact identifiers.
- Coach approval/rejection/suspension is unavailable to ordinary runtime roles. Decisions are expected-state guarded and atomically append immutable review evidence.
- Editable profile fields, Auth metadata, URL parameters and historical activation timestamps never establish approval or badge state.
- Capacity-one enforcement exists in PostgreSQL, not only in browser button state.
- One active request per athlete/occurrence and one confirmed booking per occurrence are enforced in PostgreSQL, not only in interface state.
- Acceptance and occurrence closure lock the occurrence and relevant requests deterministically so concurrent decisions cannot produce two winners or partial closure.
- Cross-run/cross-coach location identifiers, hidden coaches, self-requesting, elapsed/non-open occurrences and invalid lifecycle transitions fail closed.
- PostgreSQL enforces one active primary location for a visible coach and prevents overlapping active occurrences across all of that coach's locations; browser colors, selectors and marker state are not authority.
- Mutation errors return bounded messages without database/Auth internals.
- Browser inputs are normalized and bounded; server/domain validation is authoritative.
- Uploaded images reject unsupported types and oversized/malformed data, are decoded and re-encoded server-side with metadata removed, and use immutable owner-scoped object paths. Browser-reported names, types and dimensions are not trusted.
- Private request/booking queries are actor-scoped and reveal only necessary identity/display/time/location/status fields. Athlete responses contain no other-candidate record or aggregate count; unbounded candidate lists are never returned in one response.
- Hosted builds reject loopback/incomplete database/Auth configuration without printing values.
- Pair uniqueness, explicit recipient consent and qualifying-booking checks for connections are enforced by PostgreSQL, including cancellation/acceptance races.
- Connection-derived private data/media is revocable on removal, and bounded projections reveal neither another pair nor private coach-note metadata.
