# Coach training media: setup and recovery

[MOV-19](https://linear.app/movx/issue/MOV-19/dev0297-add-coach-profile-photos-and-mux-video) owns this implementation. The product contract is [MVP §19.5](../mvp-spec.md#195-owner-editing-and-media-sequence). This guide describes operation; it does not claim a target environment has been configured or deployed.

## Environment setup

1. Review the target migration ledger, preservation evidence and recovery procedure in [the database guide](../../supabase/README.md#hosted-changes-and-recovery). Install `20261025000100_coach_training_media.sql` after its predecessors, before deploying consumers. Existing coaches start with verified empty media; do not seed or fill their cleared content.
2. Keep the existing restricted application `DATABASE_URL`. Separately provision an environment-specific LOGIN role with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS INHERIT`, granting only membership in `app_media_worker` and database connection. Do not grant `app_runtime`, `app_owner`, table privileges, or Auth/Storage administrator access. Set this login's connection string as `COACH_MEDIA_DATABASE_URL` in the server secret store. The repository verifies restricted worker membership on every connection.
3. Select a separate Mux development environment. Create the application's server API token with Video Read and Write permission, and generate a separate signing key/private key in the Dashboard. For a deployed server, register `https://<app-origin>/api/webhooks/mux` in that same Mux environment and use that endpoint's signing secret. The application handles `video.asset.created`, `video.asset.ready` and `video.asset.errored`; Mux sends all environment events and other types are ignored. Configure all six settings listed in [.env.example](../../.env.example); restart the application. Never put these secrets in `NEXT_PUBLIC_*`, client props, tickets, logs or Git. PEM signing keys may be base64 encoded or provided as PEM text with escaped newlines.
4. Set `NEXT_PUBLIC_SITE_URL` to the exact application origin. API mutations require that origin; each issued Mux direct-upload URL is bound to it. For local testing, use the CLI forwarding procedure below or a reachable HTTPS development endpoint. Do not route development callbacks to retained production data.
5. Configure Mux usage alerts for stored minutes, delivered minutes and spend in the selected environment, with a named operator. Confirm an acceptable budget before enabling live use. This release has no automated spend circuit breaker. Limits are six photos, one current video, one pending video and four video reservations per owner/hour. The 250 MiB check is a browser preflight, so modified clients can bypass it; authoritative provider duration rejection occurs after ingest and can still incur cost. Basic quality uses the API's supported 1080p ingest cap, while signed playback is limited to 720p. Do not estimate costs as a fixed number of free videos.

Photos do not require Mux settings. If any required video setting is missing, video uploads report unavailable. A configured but unreachable provider or incorrectly privileged worker returns an unavailable/retry state; configuration presence alone is not a health check.

For the existing `movx-club-local` database, follow the [retained-local upgrade procedure](../../supabase/README.md#retained-local-coach-media-upgrade). The explicit helper backs up and verifies retained data/files, installs reviewed pending migrations and adds only the restricted worker connection to ignored `.env.local`. A successful disposable rehearsal alone does not install this schema in the normal local app.

### Local webhook forwarding

Install the [Mux CLI](https://www.mux.com/docs/integrations/mux-cli), for example `brew install muxinc/tap/mux` on macOS. CLI v3.0.0 forwards the System webhook event stream, so a Video-only app token cannot authorize this command. Create a separate CLI token with **System Read** permission and low priority in the same Mux environment; keep the application's Video Read/Write token in its environment file. The forwarding token does not need System Write, Data or Robots permissions.

```sh
mux login --interactive --name movx-webhooks
mux env switch movx-webhooks
mux webhooks listen --forward-to http://localhost:3100/api/webhooks/mux
```

Enter the CLI token's ID and secret at the interactive prompts. If this terminal exports `MUX_TOKEN_ID`/`MUX_TOKEN_SECRET`, they take precedence over the saved CLI login; remove only those shell overrides before using the separately saved CLI token. Keep the application's values in its ignored environment file.

Copy the listener's printed signing secret into the application's `MUX_WEBHOOK_SECRET`, then restart the app. This is the CLI forwarding secret, separate from any Dashboard webhook endpoint's secret. Leave the listener running during local tests. Change the forwarding port when using a disposable application stack. A connected listener proves access to the event stream; successful callback processing also requires the media migration, restricted worker connection, matching application secret and running application. A CLI synthetic event alone does not prove a real Mux upload or provider identity.

CLI v3.0.0 forwards each received event once and does not retry a failed HTTP response. A failed local callback must be replayed or reconciled through the owner controls; a retained cleanup reference is not proof of completed deletion. If Mux initially refuses deletion, cancel the failed reservation and retry its exact cleanup until the provider confirms removal. Keep the record while cleanup is pending.

The CLI implementation and scope context are in [webhook listen](https://github.com/muxinc/cli/blob/v3.0.0/src/commands/webhooks/listen.ts) and [OAuth scopes](https://github.com/muxinc/cli/blob/v3.0.0/src/lib/oauth.ts). The [Mux webhook guide](https://www.mux.com/docs/core/listen-for-webhooks) explains local forwarding and deployed delivery.

Provider references: [direct uploads](https://www.mux.com/docs/guides/upload-files-directly), [create-upload parameters](https://www.mux.com/docs/api-reference/video/direct-uploads/create-direct-upload), [signed playback](https://www.mux.com/docs/guides/secure-video-playback), [webhook verification](https://www.mux.com/docs/core/verify-webhook-signatures). Installed clients are pinned in `package-lock.json`.

## Recovery and deletion

SQL serializes all media changes for the exact owner and checks actor/dataset authority on every command. Media revisions are independent of website text/banner revisions. Published references remain until an explicit media publication switches them; a replacement never first deletes the prior published file/video.

- **Photo result unknown:** keep the selected file and retry the same submission. A successful exact retry returns the existing asset without consuming another slot. Reload media and use Finish photo upload if both normalized objects arrived. If either object is missing, cancel the reservation and select the file again; the server does not claim a failed read proves the object is absent. Cancelling queues only this reservation's private references for cleanup.
- **Video transfer interrupted:** the page offers pause/resume during transfer. Retry with the selected file and existing reservation URL while it remains valid, or cancel and select again. Reloading loses the browser's local file bytes; choose again after cancelling the pending reservation. Refresh video status reconciles provider facts without repeating upload creation. Automatic captions may finish later than video processing.
- **Video creation result unknown:** a persisted `creating` claim prevents a second external POST for the same submission ID. If an API timeout occurred before `set-upload`, the application has no provider upload ID and cannot automatically prove the result. An operator must inspect the correct Mux environment for the exact local asset UUID in passthrough, verify the upload/asset relationship against the private database record, and either reconcile through a reviewed forward operation or delete that exact orphan before cancelling the local reservation. Do not create a guessed provider identity or delete by coach name. Record IDs and observed outcome privately in the issue, omitting upload URLs/tokens/secrets.
- **Processing/failed/too-long video:** refresh status or wait for verified callbacks. A video over 60 seconds is rejected; the previous published video remains. Cancel failed uploads before trying again. Duplicate/out-of-order callbacks cannot revive retired/cancelled assets or replace a ready video with older processing state. Terminal deletion is safe to repeat; provider DELETE 404 is treated as completed deletion.
- **Cleanup pending:** retired/failed rows form a bounded exact-reference retry queue. Later owner commands retry up to twenty entries; terminal callbacks also delete rejected/cancelled provider assets. Mux can reject deletion while an asset track is preparing; the live rehearsal observed HTTP 400 with `Can't delete a preparing asset track`, followed by successful exact-ID deletion after processing finished. Preserve the pending reference and retry; never count that HTTP 400 as deletion success. Current draft/published photo references are protected by SQL/Storage locking. Failed cleanup retains the private reference and cannot be reported as complete. There is no scheduled sweep: an inactive owner may leave retired objects stored until operator reconciliation. Pending reservations expire after one hour on the next reservation, not on a timer. Monitor these records and the provider inventory during rollout; do not bulk delete a bucket or reset an account.
- **Visibility revoked:** public routes immediately stop issuing bytes/tokens when approval, visibility, dataset or publication no longer permits access. A previously issued signed Mux token can remain valid for up to five minutes; already downloaded data cannot be recalled. Emergency revocation of that residual window requires deletion of the exact provider asset or signing-key rotation with its wider impact reviewed. Do not promise instantaneous revocation of issued tokens.

No original photos are retained. Only the normalized thumbnail/full variants are recoverable. Removed media may be physically deleted after it is no longer referenced by either draft or publication. Keeping an old URL is not a backup.

## Backup, export and rollback

Before production enablement, rehearse restoration with a disposable account/dataset. Database backups include media sets/assets and the exact opaque object/provider references; they do not include Storage bytes or Mux assets. Export both normalized photo variants with a private manifest containing asset UUID, owner/dataset, order, draft/published membership, dimensions and checksums. Restrict access to this export as account data. Export owner video sources separately through an authorized Mux download/export procedure if video restoration is required; this application does not store the original video or provide a video export/download button. Verify the target environment's provider export capability rather than assuming a database restore recovers video.

Restore referenced bytes before enabling public consumers, then verify exact references, checksums, ownership, visibility and signed playback in the isolated target. Never copy development provider IDs or signing secrets into production. Keep source media under owner control if long-term re-upload recovery is required. No retained-account export or mutation is performed by the rehearsal scripts.

Roll back code using a version compatible with the additive schema. Preserve media records and external assets; use reviewed forward fixes for database behavior. Dropping the bucket/tables or replaying seeds destroys recovery evidence and is not a rollback. Removing Mux secrets disables new video uploads but is not an emergency revocation mechanism for existing signed tokens.

## Validation and release evidence

`npm run test:coach-media-db` proves fresh/upgrade SQL behavior and least-privilege owner/worker boundaries in scratch databases. Its Storage metadata fixtures do not prove actual bytes or Auth. `npm run test:coach-media-integration` uses real local Auth, restricted SQL, Storage HTTP and the production application in a wholly disposable stack for photo recovery/publication, access revocation, responsive rendering and keyboard behavior; it also runs clean-source checks. See [README prerequisites/cleanup](../../README.md#coach-training-media-validation).

For an explicit live-provider rehearsal on macOS, run `npm run test:coach-media-live -- --live`. It reads only the selected Mux values from ignored `.env.local`, builds a clean production application and starts a separate `mov19-live-mux-<random>` Supabase stack on 55521/55522/55524 with application port 3179. It creates synthetic video/speech using Chrome MediaRecorder and the local `say`/`afconvert` tools. Requirements: Docker, locked dependencies, Chrome, Mux CLI v3.0.0 and free test ports. The selected token also needs System Read for this rehearsal's private CLI listener; normal application API calls still require only Video Read/Write. It makes real provider calls and creates a bounded number of temporary video assets. It never loads retained account media or applies migrations to the retained database. The explicit `--live` flag is required; ordinary unit/integration commands do not call Mux.

The live harness creates a private CLI profile under its temporary checkout using XDG configuration/data/cache directories. It does not switch or modify the user's existing CLI login/listener, and does not write `COACH_MEDIA_DATABASE_URL` into the root environment file. That connection is supplied only to its isolated application. A temporary loopback forwarding observer preserves the exact signed body and records only event type, opaque IDs and HTTP status; it never records callback bodies or upload URLs. The test exercises owner cancellation/cleanup retries when an initial provider deletion fails, verifying pending state and preservation of the previous publication. Evidence and exact provider references are under `test-results/coach-media-live-mux/<run>/`. On success, it deletes its exact provider assets, cancels incomplete uploads, stops its exact Supabase project/volumes and verifies retained application/Auth-user/Storage hashes. An uncertain provider creation or failed cleanup retains the isolated recovery target, records failure and leaves the exact location in `recovery.json`; reconcile those references before removing it. The main app still needs a separately reviewed preservation-first database upgrade before this feature can be enabled there.

Before claiming live video complete, use a uniquely tagged approved development coach and real Mux development credentials to prove: direct resumable upload/pause/resume; matching verified callback and status refresh; exact 60-second acceptance and over-limit rejection; one pending video; cancelled/out-of-order/duplicate callbacks; signed poster and 720p playback with captions; explicit publication/replacement preserving the prior published asset; guest/other-owner/dataset privacy; hidden/suspended token denial and documented residual lifetime; expired URL/token recovery; deletion/cleanup after a provider failure; usage visibility and the agreed alert. Record concrete environment/asset IDs privately, commands, observed outcomes and exact cleanup. Provider mocks, generated RSA tokens and SQL callbacks are not this evidence. Keep MOV-19 open while required live-provider acceptance remains unverified.
