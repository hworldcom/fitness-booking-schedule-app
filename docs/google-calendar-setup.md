# Google Calendar connection (MOV-225)

This stage connects one Google account per verified MovX profile/dataset and creates a secondary **MovX** Google calendar. It preserves ordinary Google/password sign-in. Booking export (MOV-226) and Google busy-time access (MOV-227–229) remain separate, disabled capabilities. See [MVP contract](mvp-spec.md#23-optional-google-calendar-connection) and [MOV-225](https://linear.app/movx/issue/MOV-225).

## Configure a local or controlled UAT target

1. Install `20261111000100_google_calendar_connections.sql` through the target's reviewed migration process **before** enabling the feature. Follow the [database isolation/runtime/recovery rules](../supabase/README.md#runtime-authority). It adds no account provisioning/backfill or scheduling changes. Ordinary runtime inherits `app_runtime`; it has bounded function access, never direct table access or an owner credential.
2. In a Google Cloud project you control, enable **Google Calendar API** and create a separate OAuth **Web application** client for Calendar. Keep the existing Supabase sign-in client/callback unchanged. Prefer separate dev/UAT and production projects/clients; never point a test client at production. Reusing a Cloud project can couple grants/revocation across clients: local disconnect deliberately does not revoke the project's entire grant.
3. Add exact redirect URIs for the intended target:
   - Local: `http://localhost:3100/auth/google-calendar/callback`
   - UAT: `https://uat.movx.club/auth/google-calendar/callback`
   - A later separately reviewed production release: `https://movx.club/auth/google-calendar/callback`

   These are application callbacks, **not** Supabase's `/auth/v1/callback`. The flow runs on the server; it does not need a Google browser SDK or additional authorized JavaScript origins. Configure only callbacks actually used by that client's environment.

4. Configure the consent audience/test users, branding/domain/homepage/privacy and actual requested scopes: `openid`, `email`, and `https://www.googleapis.com/auth/calendar.app.created`. Record the scope's actual classification and verification requirements in MOV-225. Do not infer Calendar approval from Google sign-in branding. External/Testing Calendar authorization and refresh tokens expire after seven days; identity-only sign-in's exception does not apply. See [Google audience rules](https://support.google.com/cloud/answer/15549945?hl=en) and [scope documentation](https://developers.google.com/workspace/calendar/api/auth).
5. Set server-only variables in the local ignored configuration or target's secret store. Never send populated values in chat, commit them, expose them with `NEXT_PUBLIC_`, or include them in evidence:

   ```dotenv
   MOVX_GOOGLE_CALENDAR_ENABLED=true
   MOVX_GOOGLE_CALENDAR_CLIENT_ID=<calendar-client>.apps.googleusercontent.com
   MOVX_GOOGLE_CALENDAR_CLIENT_SECRET=<calendar-client-secret>
   MOVX_GOOGLE_CALENDAR_TOKEN_KEY=<base64-encoded-32-random-bytes>
   ```

   Generate the encryption key once using `openssl rand -base64 32`, placing it directly in the secret store. Preserve it across deployments: replacing it without a rotation window makes existing encrypted credentials unreadable. `NEXT_PUBLIC_SITE_URL` must be the exact canonical application origin (HTTPS, or literal `http://localhost:3100` locally). Missing/invalid Calendar configuration keeps connection actions unavailable; it never enables sign-in or sync implicitly. Restart the local app after changing its environment; this does not authorize resetting retained data.

6. Publish the updated privacy disclosure before inviting real users to grant Calendar access. Source changes alone do not prove the live policy is updated. Configure application/infrastructure request logging to redact OAuth callback query values; application errors never include provider response bodies, codes, tokens, verifiers or secrets. Store only sanitized status/action evidence.

## Connection and recovery behavior

Account → Connected calendars supports Connect/Reconnect, Check connection, read-only Reload status, recovery and explicit Disconnect. OAuth uses PKCE, a ten-minute single-use database continuation, a separate HttpOnly browser-binding cookie and the initiating verified ordinary Auth session/profile/dataset. The callback redirects to the fixed Account section with an enumerated notice, no proof values and no referrer. Provider hosts are fixed in the server adapter; there is no configurable provider URL or browser token storage.

Combined setup stores a strict versioned sync intent, preference version and command ID inside the existing encrypted PKCE proof. The callback activates only the completed same-owner/dataset generation through the existing restricted export command. Newer preferences or disconnect win; partial setup reads back current settings rather than retrying an uncertain write. Legacy raw-verifier continuations remain connect-only. No new scopes, public status fields, SQL migration or credentials are required. Older consumers cannot complete a new proof envelope: on source rollback, drain the ten-minute authorization window or have affected users explicitly restart connection. This does not change refresh-token encryption or justify key rotation.

Refresh credentials use AES-256-GCM with a random nonce, key identifier and profile/dataset/purpose additional authenticated data. Private tables are app_owner-owned with forced row-level security and owner-only policies; runtime gets only actor-checked functions. A normal Google token exchange without a new refresh token preserves a valid stored same-account/same-client token. The first connection proves server refresh before Connected. Later Check connection refreshes and verifies the saved calendar; it does not create events or read personal appointments.

Google can grant only part of a permission request. Connect/Reconnect explains the required app-created-calendar access; a valid authorization response missing it returns a fixed permission-required notice and preserves the previous connection. Google may present permission choices differently; do not assume there is always a checkbox. A retry is user-initiated, never automatic. Unexpected callback failures emit only a closed processing-stage/failure-category pair for server diagnostics, with no exception details, account identifiers, provider responses, URLs or proof. A missing-permission notice identifies that specific response; a generic failure must not be diagnosed as partial consent without evidence.

Reconnect renews the same Google account. Selecting another account returns a prominent “Different Google account selected” alert, preserves the current connection and directs the user to Disconnect → Connect. The alert receives focus on return; the actual connection status remains visible. Selecting another Google account never switches the MovX login.

The server commits an uncertain bootstrap marker **before** creating the calendar. It never treats a timeout as a failed creation. A known late response may record its ID after disconnect without reactivating the connection. Reconnect reuses the same-account/client mapping. Missing calendars or uncertain creation require the user to inspect Google Calendar, then either enter the existing app-created calendar ID (Google calendar Settings → Integrate calendar) or explicitly confirm a replacement. Replacement commands retain a retry identifier; replay cannot create another calendar. Neither recovery nor ordinary Disconnect deletes a Google calendar; deletion has its own separately confirmed control below.

Disconnect fences new operations and deletes locally usable credentials/pending proofs; an already-issued Google request may finish. Minimal Google subject/email/calendar/bootstrap references remain for safe reconnection until account deletion or a verified privacy-removal request. The short-lived cookie expires after ten minutes; expired encrypted pending proofs cannot be claimed and are replaced/cleared by the next connection action or account deletion. Google-account revocation is separate and can affect other permissions granted to the Cloud project, so tell users that sign-in may require consent again after revoking there.

## Key rotation and rollback

### Explicit deletion and test names (MOV-230)

Install `20261114000100_google_calendar_deletion.sql` before its consumer. It retains the original Calendar protocol behind a private wrapper and adds owner-only, forced-RLS retirement records. Normal Disconnect keeps the calendar. The separate “Disconnect and delete calendar” control requires an active usable connection and explicit confirmation that every event inside the dedicated calendar will be permanently deleted, including user-added events. Reconnect first if the calendar is already disconnected. The server chooses the exact target; browser input never selects a calendar to delete.

A durable dispatch marker precedes the Google DELETE. A timeout, missing resource or failed access check is not a confirmed deletion. Access is removed where the authoritative completion can be recorded; reload status if it cannot. A dispatched target stays retired even after disconnect, across account changes and replacement creation. It cannot be manually recovered while a late DELETE could still affect it. Reconnect before using recovery/replacement after a failed deletion, inspect Google Calendar and explicitly choose the recovery path; there is no automatic destructive retry or replacement. Confirmed deletion allows a subsequent connection to create a new calendar. Keep retirement references through application rollback; restoring a database backup cannot recover Google events.

New calendar defaults identify `MovX (Local)` on localhost, `MovX (UAT)` at uat.movx.club and `MovX` in production. Other HTTPS test origins use `MovX (Test)`. A check/reconnect upgrades a generic `MovX` name using conditional Google metadata updates after verifying app-calendar access; custom names are preserved. This does not read or edit event content. Local and UAT continue to own distinct calendars.

`npm run test:google-calendar-deletion-db` uses only unique `mov230_*` local55322 scratch databases, rehearses fresh/upgrade/atomic rollback and actual restricted-role deletion/recovery/late completion, then verifies retained app/Auth/Storage/role fingerprints and removes its exact targets. The source/provider/service and mounted UI suites use explicit fixtures. Any real deletion test needs a separately identified disposable Google calendar and operator confirmation; never use retained local/UAT calendars as fixtures. Source-only validation does not establish new hosted behavior.

Set a new `MOVX_GOOGLE_CALENDAR_TOKEN_KEY` and temporarily include previous keys in `MOVX_GOOGLE_CALENDAR_PREVIOUS_TOKEN_KEYS` (comma-separated base64 keys, at most three). A successful Check connection/reconnect decrypts with the appropriate old key and reseals credentials using the current key. Verify all retained connected rows have been re-encrypted before removing an old key; dormant accounts otherwise require reconnect. Keep previous keys through any pending ten-minute authorization window. Do not print keys or ciphertext in evidence.

Disable `MOVX_GOOGLE_CALENDAR_ENABLED` to stop new connect/check/recovery operations. Authenticated status and local Disconnect remain available when the schema exists, even without an encryption key. An in-flight request may finish, so account for its generation/bootstrap outcome. Keep additive SQL and mappings during source rollback; do not restore over later user activity, revoke unrelated sign-in grants or erase user Google calendars. Remove stored credentials only through the actor-bound Disconnect or the verified account-deletion/privacy process. A database rollback requires its own target-specific recovery plan; the migration's scratch transaction rollback is not authorization to drop populated hosted tables.

No retained migrations/provisioning or Google calls.
- `node --import tsx --conditions=react-server --test tests/server/google-calendar.test.ts tests/server/google-calendar-routes.test.ts`: provider protocol, encryption, lifecycle/error orchestration and route-rejection fixtures; no actual consent or Google data.
- `npm run test:google-calendar-ui`: actual mounted Account/connection UI with explicit Auth/API fixtures at desktop/375/320, keyboard, denial, disabled/error/recovery, disconnect and late actor-data removal. Requires Node24, locked dependencies, Chrome and free localhost3206. Owns a unique temporary app and removes it; writes safe screenshots/checks under ignored `test-results/google-calendar-ui/`.
- Run normal `npm test`, lint, typecheck, format and build from [README](../README.md#checks). An isolated tracked-source copy avoids unrelated ignored `work/` snapshots included by this checkout's broad TypeScript pattern. Do not modify/delete another task's scratch data to make checks pass.
- Real-provider acceptance requires a consenting controlled Google account: connect/deny, create/reuse, refresh, revoke/reconnect, disconnect, explicit account change, missing-calendar recovery and actual account preservation. The user handles account selection/password/two-factor/consent. Record actual client/audience/scope classification, target, observed outcomes and redacted evidence in MOV-225. Unit/UI/SQL fixtures do not establish Google UAT readiness. Production activation is a separate release.
- Separately require controlled provider-fault tests and isolated SQL tests for interrupted creation, uncertain or late results, concurrent operations and replacement replay. Both this coverage and the real-provider acceptance above are required by the [MVP acceptance contract](mvp-spec.md#233-acceptance-and-rollout).

## Optional confirmed-booking export (MOV-226)

Install `20261114000200_google_calendar_export.sql` after both connection/deletion migrations and before activating its consumer. It adds private preference, event-incarnation/mapping and separate durable-job tables; existing users remain opted out. The restricted `app_calendar_worker` role has only claim/work function execution and no direct scheduling, credential-table or Auth access. Its private recipient helper checks only an exact queued job. Canonical scheduling commits capture work without Google network calls or changes to notification delivery. Source projections set and restore the existing private booking/availability/group read flags on success and exception.

Set `MOVX_GOOGLE_CALENDAR_EXPORT_ENABLED=true` only after protected installation, current privacy publication and worker/scheduler readiness. Keep it false by default. `GOOGLE_CALENDAR_WORKER_DATABASE_URL` must use a separate restricted login inheriting only `app_calendar_worker`; never an owner, ordinary `app_runtime`, notification-worker or Supabase API credential. Preserve the existing Calendar client and encryption key. The existing `calendar.app.created` scope supports event creation, metadata lookup, updates and deletion within app-created calendars; no broader scope or new sign-in flow is added.

The separate `/api/internal/google-calendar/dispatch` cron endpoint requires the existing server `CRON_SECRET`, uses a bounded batch and network deadline, and returns only aggregate counts. Its minute schedule is independent of notification delivery; confirm that the target hosting plan supports the configured cron frequency before activation. Local development can explicitly run `node --env-file=.env.local --import tsx --conditions=react-server scripts/dispatch-google-calendar.ts` after configuring the restricted local worker. Normal startup does not provision accounts or opt anyone in. Missing delivery configuration makes enable/retry unavailable; authenticated disable and ordinary Calendar disconnect remain available when SQL is installed.

When delivery is configured, disconnected users choose **Connect & sync Google Calendar** in Account → Connected calendars. The action explains upcoming confirmed booking export before Google authorization and enables it after verified identity, offline access and calendar readiness. Existing connected users explicitly enable **Sync confirmed bookings** once; normal Reconnect preserves a paused preference. The same control later pauses/resumes export. A verified unavailable-delivery status retains clearly described connect-only staging; failed status reads require reload. Backfill processes at most 50 source IDs per discovery step and continues durably until all upcoming eligible sources and known copies have been reconciled. Each dispatch handles at most three network jobs; pending status can remain visible while a backlog drains. Private bookings include only current participants; confirmed groups include their coach and individually approved active athletes. External contacts receive no copies or invitations. Events contain generic session titles, exact booked instants, authorized snapshot location and an authenticated MovX link. No private notes, attendee list or contact details are exported.

Export off leaves existing copies in Google without updating them. Explicit disconnect/account change resets it off; same-account renewal/recovery can resume an already enabled preference. Claims recheck opt-in version, generation, lease, current source revision, target calendar and retirement before each network step. Retry uses the same persisted event ID after unknown creation results. Ownership markers and conditional etags protect mapped copies; a copy with an unexpected marker or added guests is left unchanged. Google changes never mutate a MovX booking and are not continuously monitored: failures can be discovered on later delivery or explicit retry.

Use **Retry booking delivery** for recoverable failed delivery. A missing previously exported copy requires checking Google and explicitly acknowledging **Recreate missing booking copies**; a new incarnation is saved before writing, and old references remain fenced. Missing or retired calendars use the connection recovery controls; the worker cannot create/delete whole calendars. A confirmed source cancellation removes only the applicable mapped event; completed/elapsed history is retained. Already-sent requests may finish after disable/disconnect.

Run `npm run test:google-calendar-export-db` only against its uniquely owned `mov226_*` local55322 fresh/upgrade targets. It tests atomic rollback, actor/worker isolation, canonical private/group capture, leases/recovery and original-row preservation, then removes exact scratch targets and any worker fixture roles it successfully created. `--schema-only` checks installation/rollback/preservation only and is not behavioral acceptance. Source tests use explicit provider faults; actual Google UAT and exact disposable-resource cleanup are separately required. Never use retained demo accounts or real bookings/calendars as fixtures.

Rollback disables export claims via the flag and stops the scheduler compatibly. Keep additive SQL, mappings, incarnation/job history and retirement fences; ordinary Calendar disconnect still removes credentials. Do not restore over later bookings, delete user Google history or rotate encryption keys to repair an export error. Database rollback cannot restore deleted Google events.
